# 面试讲解与追问

## 60 秒介绍

“这个项目是 RAG 的检索与证据层实验。我实现了 BM25 和字符 TF-IDF 两路召回，用 RRF 融合，并给切块保留原始行号和内容 ID。默认回答是离线原文摘录，没有调用大模型。评测把排序和拒答分开，阈值只从 dev 选择，在独立 query test 上报结果。结果发现 RRF 和 BM25 持平，检索 recall 高，但相似度拒答对同主题未知问题仍然失效。我把这些例子也放进可展开报告里。”

只讲自己已经理解、能够现场复现的部分。这里的“实现”描述代码工作，不能冒充某家公司项目或线上收入。接手后请自己运行、修改一个模块并补实验，再把经历写进简历。

## 5 分钟现场演示

1. 打开 README 的指标表，说明 12 文档、25 切块、15 个有答案测试问题的尺度。
2. 运行 `python -m evidence_rag evaluate --output outputs`，打开报告。
3. 展开 RRF 的检索成功案例，指向 chunk 的文件、行号、原文和 BM25/cosine 分数。
4. 展开 Redis 机房或 checkpoint 密码的问题：讲清为什么“找到了相关资料”仍不是“有答案”。
5. 展示 `tests/test_evaluation.py` 中修改 test 标签而 dev 阈值不变的测试，以及 `test_document_ranking.py` 中多 chunk 同源去重的测试。

## 常见追问

**为什么不直接上 embedding？**

先建立低成本、可解释、无模型下载的基线，用于校验数据和评测协议。当前字符 TF-IDF 不理解同义替换；若增加语义模型，需保留同一语料、固定 query split，并增加重排、延迟、内存和未知问题的对照。

**RRF 的 k=60 是怎么来的？为什么没有提升？**

采用经典方法的常见固定值，没有在当前 test 上搜索参数。两路都是稀疏文本表示，错误相关性强；小样本上 BM25 已经较好，RRF 不必然获胜。没有做统计显著性结论。

**如何证明没有数据泄漏？**

向量器只拟合文档，不拟合问题标签。阈值函数只接收 dev 问题，回归测试修改 test 标签后选择结果不变。但人工资料和问题来自同一作者，这仍是演示评测；要证明真实泛化，需要未接触的外部资料和新问题集。

**拒答只有 0.55 balanced accuracy，为什么还展示？**

它定位了一个核心失败模式：主题相似度不是证据蕴含。可以解释混淆矩阵中的三次 false accept 与六次 false reject，而不是通过挑成功样例掩盖限制。下一步应预先固定新 test，在 dev 加入同主题未知问题并比较 entailment 或槽位覆盖模型。

**有引用就不会幻觉吗？**

当前原文摘录可以验证来源完整性，不产生改写幻觉，但可能选错片段，或者片段只讲主题却不包含所求事实。若接 LLM，还需检查事实支持、引用是否覆盖关键结论以及拒答是否忠实。

**怎么上生产？**

优先改进真实数据、标注协议、访问权限与版本管理，再引入倒排索引、增量更新、服务化、追踪和负载测试。当前热索引约毫秒级查询不能推断生产 P95，因为没有包含并发、网络、LLM 或数据规模。

## 可以自己继续完成的练习

- 加入 30 个真实但可公开的问题，其中一半为同主题未知问题，保留人工标注流程。
- 冻结 test 后在 dev 比较不同切块预算；报告收益与退化，不只提交最好的一行。
- 在固定语料上增加一个 embedding 分支和 cross-encoder；按 qrels 比较每阶段收益。
- 将原文回答替换为显式可配置的生成 provider，新增证据支持标注；没有真实调用前不要写“已验证线上效果”。
